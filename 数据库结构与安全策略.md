## 七、身份认证链路

```
① 用户输入 4 位登录码（8888）
        ↓
② 前端查 users 表 WHERE invite_code = '8888'
        ↓
③ 拿到 user.id / user.name
        ↓
④ 存 localStorage('gl_cloud_user')
        ↓
⑤ 后续所有请求带这个 user.id 作为业务身份

CloudBase 匿名 token 只负责通过 PostgREST 的网关鉴权，
不携带业务身份，业务身份完全由前端维护。
```

**风险**：业务身份在前端，改 localStorage 就能冒充别人。

## 八、账本隔离：前端 vs 数据库

| 层 | 做了什么 | 强度 |
|---|---|---|
| 前端 | 查询带 `group_id=eq.xxx` 过滤 | 弱（可绕过） |
| 前端 | 无账本时用 `group_id=eq.__NO_GROUP__` | 弱 |
| 前端 | 切账本先清本地再拉新 | 弱 |
| 数据库 | RLS = false，无策略 | **无** |

### 实际后果

```bash
# 任何人从浏览器 F12 拿到 access_token 后：
curl -H 'Authorization: Bearer <token>' \
     'https://head-crab-.../v1/rdb/rest/records?select=*'

# 返回结果：全库所有账本的所有记录
```

**账本隔离目前只是「界面上看不到」，不是「数据拿不到」。**

## 九、风险评估

| # | 风险 | 等级 | 后果 |
|---|---|---|---|
| 1 | RLS 未开启 | 🔴 高 | 直连 API 可读全库 |
| 2 | anon 有 DELETE/UPDATE | 🔴 高 | 可删改任何数据 |
| 3 | 业务身份在前端 | 🔴 高 | 改 localStorage 冒充他人 |
| 4 | SecretKey 在代码库 | 🔴 高 | 拿到可完全控制云资源 |
| 5 | 登录码 4 位明文 | 🟡 中 | 可暴力枚举 |
| 6 | 无外键约束 | 🟡 中 | 脏数据靠代码防 |
| 7 | 无 group_id 索引 | 🟡 中 | 数据量大后慢 |

## 十、加固路线

### 第一步：密钥轮换（今天就能做）

```bash
# 腾讯云控制台 → 访问管理 → API密钥管理
# ① 新建一对密钥
# ② 更新 cloud/cloudbaserc.json 环境变量
# ③ 禁用并删除旧密钥 AKID********************（已脱敏）
```

### 第二步：收紧匿名权限（不影响现有功能）

```sql
-- 前端只做这四种操作，收回不需要的
REVOKE UPDATE, DELETE ON users FROM anon;        -- 用户只能读
REVOKE UPDATE, DELETE ON groups FROM anon;       -- 账本只增不删
REVOKE UPDATE, DELETE ON feedback FROM anon;     -- 反馈只增
```

### 第三步：补索引（性能）

```sql
CREATE INDEX IF NOT EXISTS idx_records_group  ON records(group_id, date DESC);
CREATE INDEX IF NOT EXISTS idx_expenses_group ON expenses(group_id, date DESC);
CREATE INDEX IF NOT EXISTS idx_members_user   ON group_members(user_id);
CREATE INDEX IF NOT EXISTS idx_join_group     ON join_requests(group_id, status);
```

### 第四步：数据库层隔离（根治）

需要改造认证：把业务 `user_id` 写进 JWT 的自定义 claim。

```sql
ALTER TABLE records ENABLE ROW LEVEL SECURITY;

CREATE POLICY p_records ON records FOR ALL USING (
  group_id IN (
    SELECT group_id FROM group_members
    WHERE user_id = current_setting('request.jwt.claims', true)::json->>'biz_uid'
  )
);

-- expenses / join_requests 同理
```

**前置条件**：需要一个云函数在登录时签发带 `biz_uid` 的自定义 token，
或者用 CloudBase 的自定义登录（Custom Auth）。

### 第五步：登录码强化

```
现状：4 位数字，8888 / 1111 / 2001…
方案 A：改成 8 位随机码，发给用户
方案 B：保留 4 位，但加尝试限流（同 IP 每分钟 5 次）
推荐：B 够用，门槛低
```
